### Problem it solves

> Readings from the BME280 sensor (temperature, pressure, altitude, humidity) need a place
> to be stored continuously and persistently, accessible from the cloud, so they can later
> be visualized and queried.

### Solution

> Firebase Realtime Database: a cloud-hosted NoSQL database that stores data as a JSON tree
> and pushes changes in real time to any subscribed client (the dashboard).

- [x] The Firebase project is created and the Realtime Database is active

## 3. Data Model (JSON tree structure)

> **⚠️ For AI agents:** This is the EXACT shape in which data is stored.
> Respect these field names and this hierarchy.

```json
{
  "readings": {
    "esp32-01": {
      "-NxAbc123...": {
        "ts": 1731675600000,
        "temp_c": 22.31,
        "pressure_hpa": 1013.42,
        "altitude_m": 138.7,
        "humidity_pct": 72.4
      },
      "-NxAbc124...": {
        "ts": 1731675630000,
        "temp_c": 22.35,
        "pressure_hpa": 1013.40,
        "altitude_m": 139.1,
        "humidity_pct": 71.8
      }
    }
  },
  "devices": {
    "esp32-01": {
      "name": "ESP32-01",
      "location": "San José, CR",
      "elevation_m": 1170
    }
  }
}
```

### Structure explained

| Level                | What it is                                                    |
|----------------------|---------------------------------------------------------------|
| `readings/`          | Root node grouping all readings                               |
| `readings/esp32-01/` | One node per device (allows multiple sensors later)           |
| `-NxAbc123...`       | Unique ID auto-generated by Firebase (via `push()`)           |
| `devices/`           | Root node grouping device metadata                            |
| `devices/esp32-01/`  | Metadata for one device (name, location, site elevation)      |

### Fields of each device (metadata)

| Field         | Type   | Unit   | Example         | Notes                                              |
|---------------|--------|--------|-----------------|----------------------------------------------------|
| `name`        | string | —      | `"ESP32-01"`    | Human-friendly device name (shown in the dashboard)|
| `location`    | string | —      | `"San José, CR"`| Where the device is physically placed              |
| `elevation_m` | number | meters | `1170`          | Geographic elevation of the SITE (optional)        |

> **⚠️ `elevation_m` vs `altitude_m`:** `devices/.../elevation_m` is the fixed geographic
> elevation of the location. It is NOT the same as `readings/.../altitude_m`, which is the
> value the barometer computes and fluctuates over time. Do not conflate them.

> **How metadata is created (for now):** device metadata is inserted **manually** via the
> Firebase console. A future enhancement may add a backend endpoint to register devices.

### Fields of each reading

| Field          | Type    | Unit         | Example         | Notes                                     |
|----------------|---------|--------------|-----------------|-------------------------------------------|
| `ts`           | number  | milliseconds | `1731675600000` | Unix timestamp (key for time filtering)   |
| `temp_c`       | number  | °C           | `22.31`         | Temperature                               |
| `pressure_hpa` | number  | hPa          | `1013.42`       | Atmospheric pressure                      |
| `altitude_m`   | number  | meters       | `138.7`         | Altitude derived from pressure            |
| `humidity_pct` | number  | %            | `72.4`          | Relative humidity (0–100)                 |

> **Key decision:** storing `ts` in milliseconds enables filtering by time range
> (last 24 h, 7 days, etc.) using `orderByChild('ts')` + `startAt()` / `endAt()`.

## 4. Security Rules

> **⚠️ NEVER leave the database open to the public** (`".read": true, ".write": true`).
> That would allow anyone to read or delete your data.

### Currently active rules (production) ✅

> The dashboard now reads directly from Firebase, so the rules are hardened:
> the backend writes via `firebase-admin` (admin privileges, bypasses rules), and all
> clients (dashboard) are **read-only**. The ESP32 never writes directly either — it sends
> to the backend. Therefore no client needs write access.

```json
{
  "rules": {
    "devices": {
      ".read": true,
      ".write": false
    },
    "readings": {
      ".read": true,
      ".write": false,
      "$device": {
        ".indexOn": ["ts"]
      }
    }
  }
}
```

- `.read: true` → the dashboard can read both readings and device metadata (non-sensitive)
- `.write: false` → nothing writes from any client; only the backend (via admin SDK)
- `.indexOn: ["ts"]` → keeps readings sorted by time on the server for fast range queries

> **Note on writes during testing:** the Firebase console itself has admin rights, so you can
> still add/edit data by hand there (e.g. device metadata) even with `.write: false`.

### Earlier development rules (for reference)

> These were used while building the backend, when validation on client writes still applied.
> Kept here only as historical reference — the active rules above supersede them.

```json
{
  "rules": {
    "readings": {
      ".read": true,
      ".write": true,
      "$device": {
        ".indexOn": ["ts"],
        "$reading": {
          ".validate": "newData.hasChildren(['ts', 'temp_c', 'pressure_hpa'])"
        }
      }
    }
  }
}
```

## 6. Step-by-Step Setup (no code — console only)

> This is the guide to build this layer from scratch.

```
1. Go to https://console.firebase.google.com with your Google account
2. Click "Create a project" → name it → disable Analytics (not needed) → Create
3. In the left menu: Build → Realtime Database → Create Database
4. Pick a location (closest one: us-central1) → Start in TEST mode
5. You now have the database. You'll see an empty tree and a URL like:
   https://weather-station-db-52500-default-rtdb.firebaseio.com
6. (Manual test) Click the "+" on the tree → create by hand:
   readings → esp32-01 → test → { ts: 1731675600000, temp_c: 22.5, pressure_hpa: 1013, altitude_m: 138 }
   → this shows you how a record is stored
7. Go to the "Rules" tab and paste the development rules from section 4
8. Save the credentials from section 5 for when you build the backend
```

## 7. How This Layer Connects to the Others

```
┌──────────────┐  writes    ┌────────────────────────┐  reads     ┌──────────────────┐
│ Backend      │ ─────────► │ Firebase Realtime DB   │ ─────────► │ React Dashboard  │
│ (Express)    │  admin SDK │  readings/esp32-01/... │  client SDK│  (real time)     │
└──────────────┘            │  devices/esp32-01/     │            └──────────────────┘
                            └────────────────────────┘
                                        ▲
                                        │ reads
                              ┌─────────┴────────┐
                              │ MCP Server       │
                              │ (for ChatGPT)    │
                              └──────────────────┘
```

- The **backend** is the only writer (receives from the ESP32 and stores readings).
- The **dashboard** reads both `readings` (live) and `devices` (metadata), read-only.
- The **MCP server** is read-only.
- Device metadata in `devices/` is created manually for now (no write path from clients).

## 8. Architecture Decision Records (ADR)

| Date        | Decision                                  | Rationale                                                            |
|-------------|-------------------------------------------|----------------------------------------------------------------------|
| 2026-05-20  | Realtime Database over Firestore          | Simpler for a beginner; ideal for continuous writes and real-time    |
| 2026-05-20  | Timestamp `ts` in milliseconds            | Enables range filtering with orderByChild + startAt/endAt            |
| 2026-05-20  | One node per device (`esp32-01`)          | Scales to multiple sensors without restructuring                     |
| 2026-05-20  | Writes only from the backend (admin SDK)  | Security: the client never writes directly to the database           |
| 2026-05-21  | Added `.indexOn: ["ts"]` on `$device`     | Backend queries with `orderByChild('ts')`; index keeps it fast        |
| 2026-05-22  | Added `devices/` metadata node            | Dashboard reads device name/location; injected manually for now       |
| 2026-05-22  | Activated production rules (`.write:false`)| Dashboard now reads directly from Firebase; clients are read-only    |
| 2026-05-30  | BMP280 → BME280: adds relative humidity as a fourth required field (humidity_pct, 0-100) | Sensor upgrade; all new readings include humidity alongside temperature, pressure, and altitude |
